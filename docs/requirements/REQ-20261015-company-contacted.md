# 自动记录已沟通公司
- Revision: r1
- Status: draft
- 来源：OPT-001，用户2026-10-15明确指定为名称修复后的下一需求；这是顺序授权，执行配置尚未确认。

## 目标与范围
电脑Chrome/BOSS，以公司为单位，从启用此功能起，用户成功发出任意一条消息（包括首次招呼）后自动标记已沟通；再次出现优先提示已沟通该公司岗位，不阻止浏览或继续沟通。不做职位级/跨平台查重，不导入历史会话，不手动补记。
只有确定成功发出且可靠关联唯一公司身份才落记录。点击立即沟通/打开会话/点击发送/输入清空/出现待发送气泡均不足以证明成功。发送中、失败、重试失败不记；不确定显示无法确认，不冒充未沟通过。不允许工具自动发送用于测试。
只解析必要结构状态与公司标识，不收集/保存/上传聊天正文、联系人或完整会话DOM。不新增网络拦截/MAIN world/云服务权限；若只读DOM结构无法可靠确认成功或关联公司，停在技术证据阶段报告，不交付猜测式识别。
已看过与已沟通独立保存，已沟通不改变首次看过时间；优先显示已沟通，公司仅看过仍原提示，无沟通记录不可断言从未沟通过。独立字段及CSV是否扩列、纠错撤销入口等需在执行确认前定稿。

## 证据与验证缺口
目前无实际聊天成功/发送中/失败的页面结构样本，也无联系人至唯一公司链接的可靠对应证据。不能只凭合成DOM测试宣称成功发送识别可用。GUI未授权；技术首阶段需要取得最小结构证据（不主动发送、不保存正文），可选择后续单独授权短路径检查，或用户提供脱敏结构样本。
确定性验证需覆盖成功/失败/重复事件/启动前旧消息/切会话/同公司多岗位/无唯一身份/消息晚到与撤销边界、存量数据/话术回归。真实端验收单独记录。

## 取证发现（2026-10-31，temp-evidence 真实页面样本）

- 样本：chat-open-only.html（打开未发送）、chat-sent.html（发送成功后），同一会话，用户手动 Ctrl+S 保存。
- 发送成功证据可靠：自己的消息为 `li.message-item.item-myself`（含 data-mid 消息ID），内含 `i.message-status.status-delivery`，状态文本“[送达]”；未发送样本只有 `item-friend`，无 item-myself。friend 消息无状态节点。
- 缺口1：无发送中/发送失败样本，未知对应 status 类名；设计上仅把 item-myself+送达/已读类状态当成功，其他状态不记。
- 缺口2（关键）：聊天页 DOM 无公司链接（仅全局导航菜单有 gongsi 链接），右侧职位卡（.chat-position-content）只有职位名/薪资文本，无 <a>、无 jobId 数据属性。左侧列表有公司短名展示（无类名元素），但仅显示文本，不构成唯一身份键。
- 说明：Ctrl+S 的 HTML 不含地址栏 URL，无法从样本判断聊天页 URL 是否带 jobId/securityId。需要用户提供聊天页地址栏 URL 样本（不含聊天内容）后再定映射方案。
- 候选映射方案（待URL确认）：A) 聊天URL含jobId→扩展在职位详情页建立 jobId→公司键 本地映射，聊天发送成功且有映射才记录，无映射提示无法确认公司；B) URL仅securityId→无可靠映射，功能降级为仅提示无法确认，或需要用户先在工具里看过该职位。倾向A，保守原则不变。
- 分析脚本 diff-structure/inspect-*.mjs 在 temp-evidence，随取证一起清理；HTML 不进测试 fixtures，解析规则将用合成样本重建。

### 取证补充与产品决定（2026-10-31）

- DEC-contacted-evidence-1：用户明确“有送出就算沟通”——只要出现自己发出的消息气泡（item-myself）即记录已沟通，不再要求送达/已读状态匹配；发送中/失败样本不再必需。
- 二次核对：页面上确实显示公司名“BOE”（纯文本 span，无类名）和“查看职位”（span，无 href）；职位卡整体是 div[ka=geek_chat_job_detail]，JS点击跳转，DOM 无职位/公司 URL。显示文字≠唯一身份键，不能作为公司级记录依据（同名公司/简称风险），维持“不猜测”约束。
- 会话→公司映射待确认项不变：需要用户聊天页地址栏 URL 样本，确认是否含 jobId/securityId 参数；方案A（jobId→公司键 本地映射）仍为首选。

### 映射方案定稿候选（2026-10-31，r1 修订方向）

- 证据收口：d-c 属性为组件编号（62001等，多个元素共享），非会话ID；聊天页DOM/URL均无公司键或jobId。DOM-only映射判定为不可行。
- 方案B（来源映射，首选）：用户在职位/公司详情点击“立即沟通/继续沟通”时，扩展只读记录点击上下文（页面身份+jobId+公司键，含tab）；聊天页出现首个 item-myself（有送出就算沟通，DEC-contacted-evidence-1）且该tab的来源上下文有效时，记录该公司已沟通。新tab场景用 openerTabId 关联；同tab跳转场景用 session 内该tab上下文继承。记录一次后上下文清除；来源上下文只在session保存，不落local，不改公司记录结构，仅新增沟通状态字段。
- 保守边界：直接从消息列表打开旧会话回复时无来源上下文，不记录（此时公司大概率已被首次招呼记录）；上下文存在但用户切到其他会话再发送存在误配风险，需设计缓解（如仅在该tab首次发送、检测会话列表新增节点后记录），细则开发设计并在确定性验证中覆盖。
- 待用户确认：从职位详情点击“立即沟通”后，聊天是新标签页还是同一标签页打开（影响两分支的验证重点，不改变设计）。

## 定稿补充（2026-10-31，用户确认）

- 聊天页在当前标签页打开（SPA跳转）；来源映射按同tab实现：详情页点击“立即沟通/继续沟通”记录只读上下文到该tab的session，聊天页检测到首个 item-myself 即记录该公司已沟通，记录后上下文清除。
- 手动入口（用户批准，覆盖原“无手动补记”）：我的记录列表条目在“撤销”前新增“标记已沟通”按钮；仅对已有记录公司可用，点击保存 contactedAt，来源标记 manual；已沟通条目显示已沟通状态（样式与“已看过”区分，具体开发设计），再次点击不覆盖首次时间。
- 数据：公司记录新增 contacted 字段（contactedAt + source auto/manual），与休息制度字段（REQ-20261031-weekend-label）同批实现可合并；CSV 增加已沟通列（时间与来源），保持既有列顺序兼容。
- 显示优先级：已沟通 > 已看过；无沟通记录不得显示为已沟通。撤销公司记录时沟通状态一并删除。
- 边界保持：不保存聊天正文；发送中/失败不管（有送出就算）；旧会话直接回复无上下文不自动记录；上下文误配防护（单tab首次发送清除、跨身份导航失效等）由开发实现并做确定性验证。
- 版本：与周末标签合并或单独交付由开发前确认定；当前基线0.5.1，本需求建议0.6.0。
